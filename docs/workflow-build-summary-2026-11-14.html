Workflow build: summary

2026-11-14 · coord-mcp (agent-tracking) · brief approved by Ben, decision 66bbfd41ad66

All six steps are built, tested and pushed. The read-only pages and case bookkeeping go live when the dashboard restarts. The engine and precedent apply are built but off. Ben has four decisions to make, listed at the end. Live agents and the coord MCP servers are unaffected.

What is live after a dashboard restart

  • Cases. Every task belongs to a case: one instance of a workflow per trigger, linking intent, tasks, decisions, draft and commitment. The dashboard loop keeps each case's step and who it waits on (agent, Ben, master) current. On the board as of today: 407 cases, 222 open, with 195 waiting on Ben, 24 on master and 3 on an agent.
  • /workflows (in the nav on /board and every page). For each workflow: cases, who the open ones wait on, median cycle time, Ben loose ends per case, and the three steps where cases sit longest. Below that, every open case, the one longest at its step first.
  • /brief/<meeting> and a Meeting briefs, today card on /board. A brief shows the meeting's client: open cases, live commitments, drafts not yet in Outlook, questions Ben owes, and what changed since the last meeting with that client or organizer. Today the card reads Calendar not imported for today, because the last import was 2026-11-13.
  • Definitions. One JSON file per catalog workflow in coord_mcp/workflows/defs/. Each step says who does it, which task kinds carry it, its gate, and what starts the next step. Tests check every file.

Switches

VariableDefaultWhat it does
COORD_WORKFLOW_SYNConCase bookkeeping in the dashboard loop. Writes only the case tables and the two task columns, so nothing an agent or Ben sees changes. Set it to 0 to stop it.
COORD_WORKFLOW_ENGINEoffSet it to 1 and the engine creates the next agent step's task when a result lands. It covers status request (A1), defect (A3), promotion ask (A4), FDD review (A5), FDD to production (B1) and DEVL refresh recovery (B3). It never creates a task at or past one of Ben's steps, or while a Ben loose end is open on the case. It never creates a check-in, and it never dispatches: auto-dispatch or master sends what it creates. It never drafts a reply unless there is a client message to answer. It ignores results from before it was first switched on. Each task it creates has a decision ("workflow engine; Ben may override").
COORD_WORKFLOW_PRECEDENToffAllows python -m coord_mcp.workflows precedent --apply. Apply closes a Ben loose end only when an earlier ruling of the same shape closed one like it with no work. It records one decision per loose end, citing the earlier one.

What needs a restart

  • The dashboard (the scheduled task on port 8765). It runs the case sync and the engine and serves the new pages. On its first pass it adds two tables (workflow_cases, workflow_case_events) and two nullable columns on tasks (case_id, case_step), then puts every past task in a case. The schema change is additive and does not bump SCHEMA_VERSION. Older servers read tasks with SELECT * and insert by column name, so they never see the new columns.
  • Nothing else. No MCP tool or result contract changed, so the coord MCP servers and the live client and master sessions keep running as they are.

Commands

  • python -m coord_mcp.workflows cases --open: list the open cases and where each stands.
  • python -m coord_mcp.workflows case <id>: one case with its tasks, decisions and events.
  • python -m coord_mcp.workflows backfill: put every past task in a case. Safe to run again; the dashboard does the same on its own.
  • python -m coord_mcp.workflows engine --dry-run: what the engine would create now. Writes nothing.
  • python -m coord_mcp.workflows precedent: the read-only precedent report.

What the precedent report found

Earlier rulings would settle only 3 of Ben's 685 open loose ends (docs/workflow-precedent-2026-11-14.html). Loosening the match to 0.4 still settles only 24, and most of those are the same item raised twice, not a repeat of a ruling. The repeated per-row rulings Ben makes, mostly for MAG, are rows inside workbooks under work/, not loose ends. Reading them needs openpyxl, which coord-mcp does not declare as a dependency. It happens to be importable on this machine, but nothing here relies on it.

Known limits

  • Backfill knows only where each past case stands now, not how it got there. Stall points will sharpen as the dashboard records step changes from here on.
  • Workflows are assigned by rule, so some cases are mis-tagged (analysis work filed as a status request, for example). The engine's reply guard keeps a mis-tagged case from producing an email draft.
  • Two existing tests each failed once during a slow full run and passed on every rerun: test_open_endpoint_opens_only_the_tasks_files and test_an_unchanged_list_backs_off_doubling_to_the_cap. The second compares two now() calls that can fall in different seconds.

Decisions for Ben

  1. Who imports the calendar each morning, so that briefs exist before the first meeting. Options: the hourly-triage routine's first morning run calls coord_import_meetings; master does it on its first turn of the day; or Ben does it himself. Until one of these is chosen, the board card reads Calendar not imported.
  2. Whether to turn the engine on. Run engine --dry-run first. Across the last 60 days it would have acted on one case. Turning it on means setting COORD_WORKFLOW_ENGINE=1 in the dashboard task's environment and restarting the dashboard.
  3. One new line in master's manual, needed if the engine goes on. Engine-created child tasks carry created_by: workflow engine in their spec and have a decision on record. Master dispatches them like its own tasks and does not create a second task for the same step.
  4. Precedent apply. The recommendation is to leave it off, since it would settle 3 items. The rulings that repeat are workbook rows. Reading them would mean adding openpyxl as a dependency and defining the layout of each rulings workbook. That is a separate piece of work for Ben to approve or not.
