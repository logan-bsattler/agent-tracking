Ben queue fixes

2026-11-14 · coord-mcp · follows the queue audit

All five audit fixes are built. Four are on. "Deciding for Ben" is off until Ben turns it on. They act only on results that land from now on, in sessions started after this change. Nothing already on the board was closed or changed: cleaning up the 358 existing items is still Ben's call, through the audit workbook's Confirm column.

What each fix does

Fix (audit count)When a result landsSwitch
1. Who-Ben test (144)A Ben follow-up must name a send, approval, scope or cost, access, or judgement, or carry "reason": send|approve|scope|access|judgement. Otherwise the result is refused and the error explains the test. route_for is wider: "Ask X…", "Get Y from Z", "Confirm with X" go back to the client as drafts, and edits (update, fix, re-point, draft…) as agent work. Ask, tell, confirm, whether-to and "with <Name>" no longer keep an item on Ben. A tagged item is never routed back.ben_test on
2. Repeats (65)A Ben item that repeats an open one for the same client (they share a ticket, item or file and the wording overlaps) is refused, and the error names the existing id. Two copies inside one result are refused too.ben_dedupe on
3. Covered items (60)If a result re-raises a Ben item from an ancestor task (a revision, review or re-run), the old one is closed behind a Covered: decision citing the new task, instead of the 14-day expiry deferring it. An item that says it covers <id> closes those ids too.ben_cover on
4. Workbook rule (47)A third same-shape ruling counts the client's open Ben items from the last 7 days, not just one result. The refusal tells the agent to write one workbook and hand back one item that covers the open ids.ben_group_wide on
5. Deciding for Ben (42)A new Ben item is settled when one of Ben's rulings already covers it. That is either an earlier item of his with the same shape, closed by an individual ruling, or a "Ben ruled …" decision on the same task chain that names the same anchor. It records "master default; Ben may override" citing the ruling.ben_precedent off

To see or change a switch: python -m coord_mcp.queue switch or … switch ben_precedent on, run in agent-tracking/. A switch takes effect on the next result, with no restart. python -m coord_mcp.queue landing is a dry run of what fixes 3 and 5 would close in today's queue.

What needs a restart

  • Every coord session started before this change is still running the old code. Each one runs its own server, so its results land unchecked. The new checks apply after a client clears, or once a new session opens.
  • Those older sessions also refuse the new reason field. The client CLAUDE.md text says what to do then: word the item so it says what Ben must send, approve or decide. Restart a client before relying on tags.
  • The dashboard (port 8765) needs no restart. Its /queue page still uses route_for, which now marks more items "Send to agent".

Contract and schema

  • Contract: follow_ups[].reason is a new optional enum. Results without it still validate. CONTRACT_VERSION is unchanged.
  • Schema: a new side table, follow_up_tags, is created on first use (the same pattern as follow_up_routes). No SCHEMA_VERSION bump.
  • Instructions: step 3 of all 13 client CLAUDE.md files now has the who-Ben test, and master's file has one paragraph under "Deciding for Ben". Each file has a CLAUDE.md.bak-20261114 backup beside it.

Limits

  • Duplicates are matched by wording. On the audit's duplicate pairs the test caught 12 of 53, with no false matches in 106k pairs that were not duplicates. The rest are duplicates in meaning only, so the client instructions now say to read Ben's open items before raising one.
  • The who-Ben word test would have refused about 30% of the items the audit judged genuinely Ben's (124 of 412), mostly questions. A refusal costs the agent one resend with a reason tag, so nothing is lost.
  • Hold decisions (158) and the workflow engine ignoring holds are not part of these fixes.
