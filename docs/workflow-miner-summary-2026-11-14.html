Weekly workflow miner

Internal, 2026-11-14. How new and drifting workflows reach the catalog without someone hand-writing a definition.

Bottom line

The miner is live. Every Monday at 06:30 the dashboard drafts new or changed workflow definitions from the last 90 days of the board, and puts at most 3 approval items a week in Ben's queue. Ben approves with one click on /workflows/proposed/<id> (or by answering "approve" on /queue), and the definition is adopted, recorded and backfilled. The first run will file 3 items (the B1, A1 and C3 changes below), on Monday 2026-11-16.

What it finds

  • New workflows: 5 or more untagged cases or intents with one title pattern. None today: every case tags.
  • A step the definition lacks: a task kind no step takes, in 5 or more cases. Proposed as an optional step.
  • A skipped step: an agent step 60% or more of finished cases went past without (5 or more). Proposed as optional.
  • A stall: 5 or more open cases past a step's limit, where cases that left the step took longer than the limit. Proposed as a refitted limit.

All drift for one workflow is one proposal, so Ben sees one item per workflow, not one per finding.

Commands

  • python -m coord_mcp.workflows propose: dry run. Prints the findings and what it would file. Writes nothing.
  • python -m coord_mcp.workflows propose --file: writes drafts to coord_mcp/workflows/proposed/ (gitignored) and files Ben items.
  • python -m coord_mcp.workflows adopt <id> and reject <id> [--defer]: the id is the proposal's id or its Ben item's follow-up id.

Ben's answers

  • Approve (page button, or a /queue answer starting "approve", "yes" or "adopt"): writes defs/<code>.json, records "Adopted workflow …", resolves the item and re-derives the workflow's cases. A new workflow lands with the engine off. A change keeps the workflow's engine setting, and an added step never spawns.
  • Reject or Defer (button, /queue Drop or Defer, or an answer starting "reject"/"drop"/"no" or "defer"/"later"): closes or defers the item. That proposal is never filed again. One left 14 days is auto-deferred by queue expiry and is also not refiled.
  • Any other answer goes to master as before.

Switches

  • workflow_propose (on): the weekly run. python -m coord_mcp.queue switch workflow_propose off stops it.
  • The run is stored in meta as workflow_propose_week, so it fires once per ISO week. It runs on the first dashboard pass at or after Monday 06:30, so it still catches up if the dashboard was down on Monday morning.

Schema and restarts

  • All changes are additive. The new table workflow_proposals is created on first use, with no SCHEMA_VERSION bump. Definitions can now carry an optional optional step flag and a tag rule, and the tag rules of adopted workflows run after the built-in ones. No contract changes.
  • Dashboard: needs a restart to serve /workflows/proposed and run the weekly loop (Stop-ScheduledTask / Start-ScheduledTask 'Coord Usage Dashboard', keeping COORD_WORKFLOW_ENGINE=1). Restarted 2026-11-14: /workflows shows the Proposals link, /workflows/proposed loads, an unknown id returns 404.
  • MCP servers (master, desk and the client sessions): no restart needed. The definitions loader re-reads when the defs folder changes, and new code from this change is only used by the dashboard and the CLI.
  • An adopted definition is written into the repo's defs/ folder. The next maintainer commit should include it (git add coord_mcp/workflows/defs).
